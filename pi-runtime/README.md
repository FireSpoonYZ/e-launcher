# Pi runtime for Android

Android Pi mode uses the full `@earendil-works/pi-coding-agent` SDK, pinned to **1.0.0**, with matching Pi core/AI packages. `sdk.js` owns session creation, native model/resource loading, tools, thinking levels, compaction, retries, credentials and package operations. The smaller `createPiRuntime` adapter in `index.js` remains for compatibility and regression checks.

The independent [`@e-launcher/pi-phone-control`](extensions/phone-control/README.md) extension owns `shower`, `list_apps` and `search_apps`. Android loads it through Pi's native extension loader as the named bundled extension `phone-control`; `sdk.js` only accepts generic resource-loader options and no longer registers phone tools through `customTools`. Each operation supplies native callbacks through its own loader event bus, preserving conversation isolation. The extension is included in the Android bundle and can also be packaged separately with `npm pack`.

The `shower` tool is a direct native bridge to the app's Operit Shower controller, not MCP or loopback HTTP. Node sends request-ID/call-ID tagged operations over the existing same-UID/same-PID local socket; Java validates and serializes them onto the single virtual display. Responses carry real errors, and cancellation or the 20-second timeout sends a native cancel without replay. Screenshots return PNG image content plus both virtual-display and scaled-image dimensions. Codemode scripts receive that screenshot as structured content and forward it with `image(shot.image)`; other actions still return JSON text, and failures still reject. An explicit `release` owns cleanup across Pi turns.

`schedule-tool` and `shower-context` load the same way, as named bundled factories. `shower-context` uses Pi's `context` event: `event.messages` is the deep copy of the conversation (without system messages) made before each model call, and `ctx.sessionManager` is read-only. Older Shower screenshot image parts are omitted from that copy. The latest screenshot, text, tool-call ids, and non-Shower or user images stay. Stored messages and attachments are not rewritten.

## 定时任务桥接

`schedule_task` 通过 `schedule_request` / `schedule_response` 单次转发给原生 `ScheduledTasks`，不自动重试工具的增删改请求；取消时转发 abort 信号并只发送一次 `schedule_cancel`。partial update 按当前 revision 合并，保留未提供字段及启用状态；过期 revision、任务不存在或规则无效均返回错误。create / update 支持 `alarmMode: 'alarmClock' | 'exact'`：新建省略时默认 `alarmClock`，更新省略时继承，旧持久任务缺字段按 `exact` 兼容；其他值由原生拒绝。`alarmClock` 使用 `setAlarmClock`，系统可显示下一次闹钟，入口在冷／热启动打开 `/schedules?taskId=<id>`；`exact` 使用 `setExactAndAllowWhileIdle`，不提供该系统入口，两者可切换。调度仅用 AlarmManager，不新增 WorkManager 或非精确兜底。`exactAlarmGranted: false` 或非空 `schedulingError` 表示定义已保存但闹钟尚未排上，不能承诺到点执行；权限不足等待授权，错误可供冷启动页面查看。

原生投递与恢复统一采用原定时间后 15 分钟（含边界）的补跑窗口：最多补跑一次，超窗记 `skipped / missed`，不重放多个历史周期；改时间／时区后按新本地规则重排。恢复只保存待执行并安排闹钟，不直接启动 Agent／前台服务。持久化 `queued` 可继续恢复，调用 Pi 前先保存 `starting`；仅确定未提交到 Pi 的同步启动失败最多尝试 3 次，两次重试分别延迟 60／120 秒且不得越过该窗口。可选 `attempt` 表示实际启动尝试次数，`nextAttemptAt` 为待执行／重试的 epoch ms；`queued.reason` 可为 `catch_up` 或 `startup_retry`。已接受请求不重放，旧进程的 `starting / running` 记为 `interrupted`，不自动重试不确定的外部操作。

暂停、删除或修改定义取消未开始的旧待执行项，不停止已启动会话；一次性任务自动停用保留自身待执行项。`deleteAfterRun` 仅在 `completed` 后删除未被用户修改或重新启用的定义，失败／中断保留，会话与历史仍保留；`completed` 仅表示 Pi 回合正常结束。force-stop、权限撤销、关机、首次解锁前及系统限制不保证运行；Node 启动故障可能持续到进程重启，有限重试不提供独立 Node 进程或自愈。普通定时不依赖 Shizuku，Shower 手机操作才需要。用户行为说明见[定时任务](../README.md#定时任务)；本次改动仅开发，以下既有检查说明不代表已执行，仍待集成验证。

## Configuration and sessions

The Java host supplies app-private global settings, models, credentials, system prompts and resource paths. All native/Web Pi settings pages are global-only and shared across conversations. Old workspace configuration files and package contents remain on disk unchanged, but are not applied; explicit project-scoped write requests are rejected rather than redirected. Each conversation still owns its independent cwd, attachments and work files, and workspace AGENTS/CLAUDE context discovery remains enabled. The runtime does not load the user's desktop Pi directory. Forms and file editing share those files; the next request reads a fresh snapshot. Current-chat model/thinking selection is separate from startup defaults. CLI/TUI-only settings do not control Android rendering or permissions.

Requests use the SDK model's supported thinking levels. Session snapshots include the native header and entries, preserving compaction cut points; restoring a branch can append messages after its nearest snapshot. Context is emitted in `finally`, including when a prompt throws. Android persists terminal events independently of Activity lifetime. Pending-turn checks prevent a late UI preview from replacing final text or reviving a deleted conversation. A missing known native snapshot is reported instead of silently replaying text.

Models, resource diagnostics, OAuth prompts, credential updates, package operations and resource toggles use the SDK. Provider credentials are updated through the host's conflict-checked file store. The APK includes official npm **11.6.2** and an executable launcher linked to the existing Node Mobile library. npm sources use this bundled command by default; a custom `npmCommand` takes precedence. Git sources still require Git; local packages use app-accessible paths. Configured package paths are not proof that an extension loaded successfully.

Android supplies a thin, non-TUI extension UI context for widgets, status, notifications and the question adapter; terminal/custom-editor APIs remain unavailable.

The app bundles [`builtin:todo`](extensions/todo/README.md), a MIT-licensed fork of rpiv-todo 2.12.0.
Each mutation writes an `e-launcher-todo` custom entry into the Pi session; both the tool and native/Web progress views restore from the current branch. This includes codemode-only nested calls, subsequent turns, branch navigation and compaction. Runtime factories keep separate state even when conversations share a cwd. Old direct tool-result snapshots remain readable; pre-fork codemode sessions can import their saved Android `.ui.json` once when no structured branch state exists. No standalone `.pi/todo.json` is created.

Remove the old `npm:@juicesharp/rpiv-todo` package in Pi resources to use the bundled implementation: like other replaceable built-ins, `builtin:todo` yields to a third-party `todo` tool. It can be disabled with `-builtin:todo`. The original wire tag `@juicesharp/rpiv-todo` is retained for existing Android/Web snapshots. The task widget still shows question status and opens the conversation/detail screen for answering.

## MCP servers

Both the native MCP settings category and the web MCP resources page manage real servers, not extension packages. They support stdio and Streamable HTTP; legacy SSE is rejected. Add, edit, remove, enable/disable, check/reconnect, tool listing, and OAuth sign-in/sign-out use the existing settings-query/auth-reply bridge. The form exposes name, transport, URL or command/JSON args, enabled state and exposure; its advanced server JSON preserves unedited fields such as env, headers, oauth, timeout and cwd. The full mcp.json editor can also repair invalid entries or edit top-level options.

Chat explicitly loads the official replaceable built-ins MCP, codemode and tool_search, respecting -builtin:mcp / -builtin:tool_search and third-party replacements. The settings page warns when the built-in MCP implementation is disabled or replaced: a successful standalone check then does not mean chat will load these servers. Default exposure is codemode (discover/call in scripts); direct declares tools to the model, deferred uses tool_search, and hidden is unreachable. MCP tools pass through Pi's native tool pipeline. Phone-control, Shower and schedules remain native extensions, not MCP servers.

MCP configuration is loaded only from the supplied app-private agentDir/mcp.json. The application does not load cwd/.pi/mcp.json or project settings/resources/packages/system prompts; old project files are retained without migration or deletion. The underlying SDK still supports project scopes, while this app-owned integration selects global-only configuration without changing conversation cwd/context discovery. Existing files are not migrated or replaced with defaults. Server mutations use the official validation/editing helpers and Node file lock with a whole-file revision check. Both first-party full-file editors save global mcp.json (including canonical relative aliases) through mcp_file_save under that same official lock and lock-internal CAS; supplied source, numeric spelling, atomic replacement and previous-edition backup are retained. Invalid entries are reported and skipped; disabled entries are listed without connecting. The upstream file editor cannot safely add the reserved __proto__ name, so the settings API rejects it explicitly.

A check reports the last actual initialize/tools-list outcome (connected, needs-auth or failed), its time and tool descriptions, then closes the connection. It is not a permanent connection indicator. Each chat turn owns and releases its connections and transports, including still-initializing background servers. Normal disposal cancels runtime-owned HTTP work and awaits transport close before disposing the official session. Standard node uses the existing node-to-native-launcher symlink plus PATH/LD_LIBRARY_PATH; npm and npx commands are adapted to the packaged npm-cli.js/npx-cli.js through the official transport factory without rewriting user configuration or implementing another MCP client. Arbitrary binaries, native npm addons, uv and Python still depend on what Android can execute.

OAuth uses the official signInMcpServer and credential store, with browser authorization URLs and pasted redirects forwarded through auth/auth_prompt/replyAuth. Tokens stay in the supplied agentDir/mcp-auth.json (not model auth.json); the generic credential editor requires explicit consent. Checks omit raw env/header values and tokens. HTTP/OAuth error response text is suppressed in favor of state and HTTP status, including JSON-RPC errors and thrown OAuth failures; stdio diagnostics redact already-resolved secrets. Diagnostic handling does not rerun credential commands or fetch/refresh credentials again. Desktop protocol/OAuth fixtures test redirect success, sign-out, cancellation/error listener cleanup and child shutdown; real browser authorization and external servers still require device verification.

## Bridge and packaging

The app starts Node once with private `HOME`/`TMPDIR` and exchanges request-ID-tagged newline JSON over a randomized abstract Unix socket. The connecting peer must match the app process UID and PID. One operation per conversation is admitted at a time; independent conversations may run concurrently. The protocol includes busy rejection, cancellation, errors, OAuth replies and call-ID-tagged Shower requests. Startup failure is sticky until process restart.

`scripts/prepare-pi-runtime.ps1` prepares Node Mobile 24.18.0-0, arm64 libraries/headers and npm dependencies. `npm run build:android` bundles `android.js` into `app/src/main/assets/pi-runtime.cjs` and copies the pinned SDK metadata, documentation, themes and export resources into `app/src/main/assets/pi-sdk/`. The build also copies the complete pinned npm distribution to `assets/npm/11.6.2/`. These outputs are generated and ignored by Git. Gradle packages the Node executable as `libnode_launcher.so`, with native-library extraction enabled so Android can execute it from `nativeLibraryDir`. The app prepares npm in a versioned private directory and repairs its `node` symlink after APK replacement. The bundle maps `import.meta.url`, sets `PI_PACKAGE_DIR`, and uses the pinned SDK's internal HTTP dispatcher bootstrap. SDK examples are included with the docs. `pi-sdk/quickjs.wasm` and `codemode-worker.js` provide codemode; `photon_rs_bg.wasm` and `image-resize-worker.js` sit beside `pi-runtime.cjs` so both CJS `__dirname` and the ESM resize worker resolve Photon without a developer `node_modules`, executable-directory fallback, or session cwd dependency. Photon is Rust/WASM, not an Android `.node` addon. Java startup and instrumentation copy these same resources, and Gradle tracks them as outputs.

The Android entry registers upstream static OAuth and Bedrock loaders for the otherwise variable dynamic imports. esbuild resolves all named `pi-ai` imports from the runtime's package scope, keeping loader registration and the SDK on one registry even when npm installs a nested copy. ChatGPT login supplies upstream's synchronous `getDeviceId` callback; only a flow requesting it creates a global installation UUID, emitted through the existing settings/CAS path before auth/prompt events and flushed even on cancellation/failure. Existing global IDs are reused; project IDs and analytics/tracking settings are untouched.

Pi 1.0.0 `models.generateImages()` is available in codemode with session credentials. `image(block)` processes its output through Photon and the existing tool-image/chat-attachment projection; no separate image-generation UI is added.

## Local verification

```sh
npm --prefix pi-runtime ci
npm --prefix pi-runtime test
```

The suite checks all 71 documented settings keys plus the bundled title setting (72 controls), exact installed Pi 1.0.0 versions, wire-level thinking values, scoped resources, local package lifecycle, native history/compaction, session-only selection, cancellation and context publication after a throwing prompt. It also checks the Shower tool schema boundary, native dispatch, screenshot image projection, errors and cancellation, scheduled-task registration and one-shot native routing, context pruning against an unchanged history, then builds and executes the shipped CJS bridge with a simulated Java Shower response plus local mock SSE, TypeScript extensions/tools/providers, simulated OAuth and busy/abort/recovery checks. Mock native/provider replies are not device or provider validation.

The npm integration check uses a loopback npm registry and mock model to exercise the shipped bundle: scoped/versioned package installation, dependencies and `postinstall`, `node` and `process.execPath`, persisted settings, fresh TypeScript extension loading, same-chat next-turn tool execution, filtering, workspace precedence, ordinary npm packages, load errors, repeated installation and removal. It makes no real model requests. It additionally copies the runtime payload into an isolated directory outside the repo, verifies the shipped SDK version and Photon WASM, executes the real resize worker and image `read`, checks the four built-in factories, codemode's nested structured bash results (exit 0 and 7), mock-provider `models.generateImages()` credentials/history/chat-image projection, and bundled OAuth loaders/global device-ID generation/reuse/persistence on cancel/failure.

The shared mcp-check.cjs fixture additionally exercises real initialize → tools/list → tools/call through the official HTTP and node stdio transports, plus npm/npx stdio handshakes. SDK prompts discover/call tools through direct, codemode and deferred exposure. It checks project overrides, disabled servers, invalid/stale writes, failed/needs-auth states, provider-token restrictions, builtin disable/replacement, OAuth redirect/credential isolation/sign-out, listener cleanup after cancel/error, and child cleanup after an aborted initialize. The npm fixture now also publishes a real v1→v2 update, verifies the same Node process and same-chat next turn executes the v2 extension, keeps explicitly pinned sources pinned, and verifies global updates leave old project package/settings bytes unchanged. Successful package operations clear the upstream extension cache; ordinary chat turns do not clear it. Community installation is unpinned by default, while manually supplied versions and existing pinned records are not automatically rewritten.

The same fixture runs against the shipped CJS bridge from a temporary directory without repository node_modules. Focused review regressions cover ordinary chat completion during stalled stdio/HTTP initialization, echoed credentials and thrown OAuth failures, full-file alias/backup writes, and a controlled official-lock interleaving of full-file and server mutations. To run only shipped MCP checks on desktop after bundling, use `node app/src/androidTest/assets/npm-check.cjs pi-runtime/node_modules/npm/bin/npm-cli.js app/src/main/assets/pi-runtime.cjs --mcp-only`; this skips the unrelated registry/Photon integration checks. The Android instrumentation entry remains `checks=npm`.

Run `scripts/verify.ps1` after the runtime suite for JVM tests, pure Java checks, APK assembly and lint. Build `:app:assembleDebugAndroidTest`, install the app and test APKs with `adb -s <serial> install -r`, then run:

```sh
adb -s <serial> shell am instrument -w -e checks npm com.example.launcherprobe.test/com.example.launcherprobe.ChatStoreChecks
```

This runs the same npm integration script from the target application's UID, using isolated files/cache directories. It also checks npm resource reuse and dangling launcher-link repair, then runs the same Pi 1.0.0/plugin/Photon/codemode/image/OAuth and MCP protocol fixture checks described above. The entry is checks=npm; there is no separate checks=mcp entry. Native Shower/apps/schedule callbacks in this entry are simulated; it does not control the device or create real tasks. It never reads real credentials or modifies chat settings. Passing desktop Node/JVM checks alone does not establish Android execution, real OAuth, native-addon or arbitrary extension compatibility. After the App-UID fixture check, separately add a trusted external MCP server in the native/web UI, check its real tools and errors, and invoke a harmless tool from chat. Verify the actual third-party node/npx package or HTTP endpoint on the device, not just the fixture. For OAuth servers, verify browser/pasted-redirect success and cancellation/sign-out without exposing tokens in screenshots or logs.
